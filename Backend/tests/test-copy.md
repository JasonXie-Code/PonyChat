不要加代码级别的兜底替换、正则改写、输出清洗，只通过提示词优化和字段调整优化结果。


测试后端角色回复时，必须在Server-USA服务器上，使用全新的随机测试用户，测试用户的会员等级为 developer 。避免污染真实用户或既有对话数据。测试角色以 System 用户下的 紫悦 碧琪 珍奇 苹果嘉儿 云宝 柔柔 这些角色为基准，但不要直接用测试用户请求 System 的角色 ID；应先为随机测试用户临时克隆一份 System 角色资料，再使用这些临时克隆角色进行测试，确保测试命中真实角色设定，同时不会写入 System 用户或真实用户的对话记录。


测试内容按当前矩阵执行：对每个 System 角色分别测试 3 类场景（根据修改的内容规划测试场景），角色之间可以并发执行，每个角色内部按场景顺序执行，便于定位失败。


测试完成后必须清理所有测试数据，包括随机测试用户、临时克隆角色、测试对话、消息、普通对话记忆、情绪状态、图片上下文、主动任务、用量记录、会员记录等与该测试用户相关的数据。清理后需要确认测试用户和临时角色数量均为 0，例如 left_user = 0、left_chars = 0，再认为测试结束。








**稳定测试流程**

1. **先定位问题**
   - 从 `.chatlogs` 找到出错轮次：Step 1、Step 2、Step 3 请求和响应都看一遍。
   - 先判断错误来源：
     - Step 1/2 已经给错材料：修提示词/字段/材料传递。
     - Step 3 自己幻觉：修 Step 3 输出字段或执行提示。
     - 记忆/场景错误：修记忆摘要、场景锚点、事实边界。
   - 不直接按最终回复打补丁，先找“错误材料从哪一步进入”。

2. **本地只做静态验证**
   - 改完后先跑：
     - `python -m py_compile ...`
     - 相关单元测试。
   - 本地测试只确认代码、提示材料、字段结构正确。
   - 不用本地大模型调用当验收结果。

3. **全量部署到服务器**
   - 每次真实验证前都先部署：
     - `python Backend\deploy\deploy_backend_server_usa.py`
   - 必须看到 health 的 `deploy_token` 一致，确认新进程加载了新代码。
   - 测试命令使用服务器环境：
     - `/opt/ponychat/.venv/bin/python`
   - 不用本机服务验证后端角色回复。

4. **创建隔离测试用户**
   - 每轮测试创建全新的随机用户。
   - 会员等级设为 `developer`。
   - 用户资料按测试需要设置，比如人类、小马、无特殊资料等。
   - 测试结束必须清理，并检查：
     - `left_user = 0`
     - `left_chars = 0`
     - `left_conversations = 0`
     - `left_messages = 0`
     - `left_normal_chat_memory = 0`
     - `left_character_memories = 0`

5. **克隆 System 角色**
   - 不直接请求 System 用户下的角色 ID。
   - 先把 System 角色临时克隆到随机测试用户下面。
   - 默认测试角色用：
     - 紫悦
     - 碧琪
     - 柔柔
   - 只有涉及角色广泛差异、上线前回归或问题明显依赖 6 角色时，再扩展到：
     - 紫悦、碧琪、珍奇、苹果嘉儿、云宝、柔柔

6. **矩阵执行方式**
   - 角色之间并发。
   - 同一角色内部按场景顺序执行。
   - 默认每个问题设计 3 类场景：
     - 直接询问：确认核心事实。
     - 反向诱导：用户给一个错误说法，看角色是否纠正。
     - 自然场景：放进普通对话/剧情里，看是否稳定应用。
   - 如果是复杂问题，可以扩展到 5 个场景，但先用 3 角色控制成本。

7. **每个测试必须保存原文**
   - 输出里必须包含：
     - 测试用户
     - 克隆角色 ID
     - 原始用户问题
     - 原始角色回复
     - 每条 check 的结果
     - failures 列表
     - cleanup 结果
   - 不能只写“通过/失败”，否则后面不好判断是不是误判。

8. **验收标准**
   - 单点修复：3 角色 × 3 场景全过，或者真实问题复现上下文必过。
   - 模糊判断类问题：90% 以上通过即可。
   - 高风险流程改动：先 3 角色 smoke，通过后再 6 角色矩阵。
   - 如果失败是模型偶发但材料正确，记录原文，先观察；如果失败来自 Step 1/2 错材料，就继续修流程。

9. **推荐测试设计格式**
   ```text
   问题：
   修复点：
   期望不变量：
   禁止项：
   测试角色：
   测试场景：
   1. direct_fact:
      user:
      expected:
      forbidden:
   2. correction_challenge:
      user:
      expected:
      forbidden:
   3. natural_scene:
      user:
      expected:
      forbidden:
   通过标准：
   清理检查：
   ```

10. **可复用矩阵组件**
   - 新增后端角色回复矩阵时，优先复用 `Backend/scripts/matrix_test_common.py`。
   - 新脚本只需要保留三类内容：
     - `SCENARIO_KEYS`：场景 key 列表。
     - `build_scenario(char, key)`：构造 `ScenarioInput`，写清原始用户问题和上下文消息。
     - `validate_step(key, result, scenario, char)`：返回 `passed/checks/failures/raw_role_reply`。
   - 公共组件会统一处理：
     - 创建随机 developer 测试用户。
     - 克隆 System 角色到测试用户。
     - 角色并发、角色内场景顺序执行。
     - 标准化输出 `SUMMARY / ROLE_RESULTS / FAILURES / CLEANUP`。
     - 清理用户、克隆角色、对话、消息、记忆、情绪/场景/图片状态、关系状态、主动任务、用量和会员记录，并在 cleanup 非 0 时失败。
   - `Backend/scripts/test_choice_attribution_matrix.py` 是推荐样板。

11. **当前最佳实践**
   - 修提示词/字段优先，不做输出清洗。
   - Step 3 只当“看材料写回复”的执行层。
   - 模糊问题交给模型判断，但要把上游材料整理清楚。
   - 真实验收一定在服务器完成。

12. **可复用测试总流程**
   - 先判断测试类型：
     - 前端纯 UI：样式、布局、滚动、加载态、空态、导出图片、主题色。
     - 前端状态/持久化：冷启动、重进 App、切换页面、图片/语音/草稿/任务状态恢复。

   - 每个问题先写清：

     - 留证方式：
   - 能本地确定的问题优先本地自动化验证；需要真实模型回复的问题必须部署到 Server-USA 后验证。
   - 前端效果可以用调试面板或本地注入测试数据验证时，不要为了 UI 验收额外消耗后端模型调用。
