# 数据防护边缘情况检查报告

> 文档状态：2026-08-09 已复核。本文是计划或审计记录，结论对应其记录时点；当前实现与风险以 `docs/PROJECT_STATUS.md` 和代码为准。

## 一、已覆盖或已加固的边缘情况

### 1. 删除进行中与同步的竞态
- **场景**：用户在本设备删除对话的同时，另一设备触发 `data_saved` 同步，本设备收到事件并执行 `loadConversationsFromBackend`，可能用旧列表覆盖本地“已删除”状态。
- **现状**：`_deletionInProgressChars` 在删除流程中标记角色，sync 在**入队时**和**执行时**都会检查，若事件涉及该角色则**跳过**整次同步（含 loadConversationsFromBackend），避免覆盖。
- **结论**：已防护。

### 2. 部分同步角色被误删
- **场景**：角色尚未完全从后端拉取（只加载了列表未加载详情），若此时用“前端列表”做差异删除，可能把后端有但前端未加载的对话删掉。
- **现状**：前端把 `partially_synced_characters` 传给后端；后端对名单内角色**不执行**“后端有而前端未传则删除”的逻辑，只做写入/更新。
- **结论**：已防护。

### 3. 紧急恢复时把“刚删的对话”恢复回来
- **场景**：用户删除对话后很快刷新或切回页面，5 分钟内紧急恢复从备份合并数据，若备份里还含该对话会再次出现。
- **现状**：
  - 删除时已用 `writeEmergencyBackupToAllSources` 更新多源备份，备份中已去掉该对话。
  - init 恢复时用 `_recentlyDeletedConvIds` 过滤备份中的对话，**仅在此处**将“视为已删除”的窗口从 30 秒延长为 **5 分钟**，与紧急恢复窗口一致，减少多标签页或陈旧备份把已删对话恢复回来的可能。
- **结论**：已防护并加固（5 分钟过滤窗口）。

### 4. 多设备删除同步
- **场景**：设备 A 删除对话，设备 B 需同步删除。
- **现状**：后端在 `conversation/delete` 成功后广播 `conversation_deleted`（带 `deleted_conversation_id`）；设备 B 的 sync 收到后调用 `markAsDeleted` 并从本地列表移除，再刷新 UI。
- **结论**：已覆盖。

### 5. 空数据 / 更少数据覆盖
- **场景**：网络异常或前端发空/更少数据，导致后端被误覆盖。
- **现状**：`save_intent === 'auto_sync'` 时，后端拒绝“用空或更少对话/Galgame 覆盖已有”；仅 `user_edit` 或专用删除/重置接口允许。
- **结论**：已防护。

### 6. Galgame 重置与保存
- **场景**：用户点“重置”后，前端发空消息列表，若按“防误删”会被拒绝。
- **现状**：重置走专用接口 `/galgame/reset` 直接清库；前端再保存时要么带 `user_edit`（若有后续用户操作），要么后端已为空，`existing_count === 0` 不会触发“更少覆盖”的拒绝。
- **结论**：无问题。

### 7. 已删除记录的清理
- **场景**：`_recentlyDeletedConvIds` 无限增长。
- **现状**：`cleanupDeletedRecords()` 在 `loadConversationDetail` 的合并逻辑中被调用，会清理超过 30 秒的条目。
- **结论**：已处理。

## 二、已知限制与修复结论

### 1. 多标签页备份互相覆盖
- **场景**：标签 A 删除对话并更新备份；标签 B 仍持旧状态，在 visibility hidden 时写入紧急备份，可能用“含已删对话”的状态覆盖 localStorage/Android/IndexedDB。
- **影响**：若之后只读到一个源（或按 timestamp 取到 B 的备份），已删对话可能被恢复。
- **缓解**：删除时已写回多源、init 恢复时 5 分钟内按“已删除”过滤，可显著降低概率；彻底解决需多标签协同（如 BroadcastChannel 通知其他标签更新状态/备份）。
- **建议**：文档说明“多标签同时开时，删除后尽量在操作删除的标签页多停留几秒或刷新另一标签”。

### 2. 启动时紧急恢复只读 localStorage
- **场景**：最近一次紧急备份只写进了 IndexedDB（例如 localStorage 满），未写进 localStorage；启动时 5 分钟恢复只读 localStorage，可能看不到最新备份。
- **影响**：该次启动可能少恢复一部分数据；后续进入对应角色时 `loadConversationDetail` 仍会从多源备份尝试恢复。
- **建议**：可选优化为 init 阶段使用 `loadEmergencyBackupFromAllSources()`（需保证 conversations.js 先于 init 加载或把该函数挂到 window），用“多源最新”做 5 分钟恢复。

### 3. 离线删除“看起来被撤销”
- **场景**：用户离线时删除对话，前端从内存和备份移除并请求 `conversation/delete`（失败）；恢复在线后 sync 执行 `loadConversationsFromBackend`，后端仍含该对话，列表会再次出现。
- **影响**：删除在服务端未生效，行为与“删除失败”一致。
- **建议**：可文档说明“离线时删除需联网后再次确认列表”；若要做“离线待删”需额外设计（如 pending_delete 标记 + 重试）。

### 4. “最近删除”在 applyDataToMemory 中仅 30 秒
- **场景**：合并服务器与本地时，`isRecentlyDeleted(id)` 超过 30 秒即视为未删除；若服务器因延迟仍返回该对话，31 秒后会被重新加回本地。
- **影响**：通常 30 秒内后端已收到删除并持久化，下一轮加载就不会再返回该对话；若删除 API 长期未成功，对话再现与“删除未生效”一致。
- **结论**：与离线删除同属“删除未持久化”的已知限制，当前逻辑可接受。

## 三、本次改动摘要

1. **删除后紧急备份写多源**（已在上次完成）  
   删除对话后通过 `loadEmergencyBackupFromAllSources` + `writeEmergencyBackupToAllSources` 更新所有存储，避免仅更新 localStorage 导致 Android/IndexedDB 仍保留旧备份。

2. **init 紧急恢复的“已删除”过滤窗口延长为 5 分钟**  
   init 中过滤备份里的“最近已删除对话”时，由 30 秒改为 5 分钟（与 5 分钟内才做紧急恢复的窗口一致），降低多标签或陈旧备份在刷新时恢复已删对话的概率。

## 四、测试建议

- 单设备：删除后立即刷新、30 秒后刷新、5 分钟内刷新，确认已删对话不重现。
- 多设备：设备 A 删除 → 设备 B 列表与详情中该对话消失。
- 多标签：标签 A 删除 → 标签 B 切后台触发备份 → 关闭 A、刷新 B，观察是否出现已删对话（可接受偶发，见上文“多标签页备份互相覆盖”）。
- 离线：离线删除 → 恢复在线后 sync，对话可能 reappear，符合当前“删除未持久化”的预期。
