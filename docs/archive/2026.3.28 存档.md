# PonyChat 项目近况说明（2026-03-28）

> **写给点进这里的您**：这是一份面向关心 PonyChat 的朋友的说明。我们会用尽量直白的句子告诉您：**团队为什么暂时放慢节奏**、**您使用的客户端大致会怎样运转**，以及**若有一天重新加速，我们会先看什么**。文中仍保留部分技术名词，方便您愿意深挖时对照。

## 一、为什么近期会放慢节奏

团队在一段时间内会**少做大规模新功能**，主要不是否定过去的工作，而是：在现有大模型生态里，我们很难同时把「心里那款产品」稳稳做出来，所以先**收一收、把话说清楚**，等模型能力再上一个台阶，再决定是否全力冲刺。

### 1. 「亲密关系向叙事」与「中文自然表达」很难两头兼得

- 实际试下来：**更擅长亲密关系、破限向叙事的模型**，往往在**中文自然度、修辞和长篇连贯**上，会弱于主流中文商用模型。
- 反过来：**中文聊得顺、适合长期日常对话**的模型，在**亲密关系向的深度与可控性**上，又常常达不到我们对产品的预期。

这不是简单「换一个模型」就能解决的事，也和供应商策略、合规与训练数据有关；短期内很难靠堆工程补丁彻底抹平。

### 2. 陪玩、剧情向体验，对模型与链路要求更高

- **聊天陪玩**（弹幕、语音、实时能力、操作 Agent 等）和**规划中的剧情模式**（独立故事线、状态与结局），都依赖：**成本可控、延迟可接受、上下文够长、指令跟得稳**的模型与整条链路。
- 以当时方案看，**费用、首字快慢、多模态稳定性、多步生成的一致性**还不足以让我们放心「继续在这两块大举投入」。
- 剧情向的设想在内部设计文档里有过框架，**尚未**做到和「日常聊天 + 陪玩」同等规模的交付；继续推进同样会撞上上面说的能力天花板。

**我们想让您明白的一点**：放慢节奏，不等于否定已经写下的代码与文档；我们是把瓶颈更多归因于**模型这一代的能力边界**，避免在原地无限堆提示词和分支，却把体验带偏。

## 二、若您想了解「背后大致长什么样」（技术快照）

以下记录的是**封档日前后**工程上的状态，方便您对照自己使用的客户端与服务端；路径、文件名会偏技术，您可只看小标题与表格。

### 1. 技术栈一览

| 区域 | 技术 | 对您大致意味着什么 |
|------|------|-------------------|
| 后端 | Python、FastAPI、SQLite 等 | 对话与数据跑在服务进程里 |
| Android | Kotlin、Jetpack Compose | **聊天与陪玩的主客户端**（官网不提供浏览器里完整聊天） |
| Web | 网页与后台 | 宣传页、管理入口等；历史浏览器版仅仓库保留 |
| 数据与工具 | 小马知识库管线、脚本等 | 给对话与维护用的资料与工具 |
| 部署 | 多环境与文档 | 服务如何部署、证书与机器分工见仓库文档 |

更细的目录约定见仓库内 `PROJECT.md` 的说明表。

### 2. 对话模式：您发消息时，后端大致怎么做

- **日常聊天**：在当时的策略下，主对话会**统一走约定的默认轻量模型**，不再随您在模型大厅里选的「当前模型」随意切换（具体以您连接的服务端版本为准）。
- **旧的游戏向 / 锁分向模式**：服务端会对旧请求返回**已下线**提示，请您**升级客户端**；历史上相关玩法的代码已从主在线链路拆出，**数据库里可能仍留有旧表**，仅供迁移或查历史，**不代表产品仍提供该玩法**。
- **摘要与检索**：摘要流程会尽量不误伤正常内容；小马知识库检索主要在**日常聊天**里起作用，并可由服务端配置关闭。

### 3. 模型与「模型大厅」

- 服务端会接入多家模型厂商，并由「模型大厅」管理列表与参数。
- 在**上述「日常聊天统一默认模型」**策略生效时，大厅里某些选项对**主对话**的实际影响，要以您所用版本的策略为准；**陪玩等独立链路**可能另有固定模型。

### 4. 陪玩相关

- 陪玩主对话会使用**单独约定的轻量模型**，一般**不**随您在聊天里选的模型变化。
- 语音、实时链路等能力会持续迭代；操作类陪玩涉及系统能力与客户端服务，细节以当时版本为准。

### 5. 官网与浏览器里能做什么

- 官网侧重**介绍与运维入口**；**不能**在公开网页里完成与 App 里同等的长期对话与剧情试玩。
- 旧书签若指向历史聊天页，一般会**跳回介绍页**（以实际部署为准）。

### 6. 剧情向体验（规划）

- 内部有过设计文档；封档日前**尚未**与「日常聊天 + 陪玩」同等规模合入主线。若将来重启，会重新评估成本与叙事质量。

### 7. Android 客户端

- 版本号以应用内与发布说明为准（封档时仓库内曾标 **3.2.2** 一类信息，以您设备为准）。
- 聊天、角色、模型大厅、陪玩服务等均在客户端工程内持续维护。

### 8. 运维与发布（给自建或对接服务的您）

- 若您自行部署，服务器拓扑、证书与分发路径以仓库内 `SERVER.md`、`deploy/` 下说明为准；应用包分发路径亦在文档中有约定。

## 四、若重新加速开发，团队会先核对什么（内部检查思路）

1. 下线策略与「日常聊天用哪类模型」是否仍符合产品定位。  
2. 配置文件、密钥与环境变量是否仍然有效、安全。  
3. 从备份恢复数据库前，尽量先做只读检查，再跑迁移或工具脚本。  
4. 陪玩与实时链路若接第三方，计费与配额是否变化。  
5. 若未来允许「日常聊天可选多种模型」，需同步改策略、客户端提示与会员规则，避免和旧逻辑打架。

## 五、写在最后

封档整理时，仓库里仍有一套**能跑的后端、Android 主路径、网站与后台、陪玩相关子系统**等工程基础；我们暂停的主要是**产品节奏与这一代模型能撑起的野心**，而不是说这一切都没有价值。

若日后择期重启，团队会更愿意先用**模型评测与成本测算**说话，再决定剧情向、陪玩向要投多深，少做「提示词和分支无限膨胀、底座却不升级」的消耗。
