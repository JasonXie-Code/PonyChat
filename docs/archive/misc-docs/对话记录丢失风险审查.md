# 对话记录丢失 / 被清空 — 代码审查报告

## 一、已有防护（现状概览）

- **后端防误删**（`backend/routes/characters.py`）：`save_intent=auto_sync` 时禁止用更少消息/对话覆盖；`user_edit` 时才允许清空或减少。
- **前端合并逻辑**（`applyDataToMemory`）：服务器返回空对话时保留本地；本地比服务器新时做 SmartMerge，不覆盖。
- **紧急备份**：`beforeunload` / `pagehide` / `visibilitychange` 时写 `_emergency_backup`（localStorage + Android + IndexedDB）；清缓存时保留 `_emergency_backup`。
- **登出**：`resetAppState` 清空内存并调用 `clearEmergencyBackup()`，避免跨用户泄露。
- **保存失败补写**：`_lastSaveFailed` + `visibilitychange` / `online` 时重试保存。

---

## 二、可能丢失或清空的场景与边缘情况

### 1. 清空缓存并刷新（长时间不切页）【✅ 已修复】

- **位置**：`js/utils/system-utils.js` — `clearCacheAndReload`；`js/conversations.js` — 紧急备份仅在 `pagehide` / `visibilitychange` 时写入。
- **场景**：用户长时间不切换标签页、不最小化，只在当前页聊天，然后点击「清空缓存并刷新」。
- **结果**：`_emergency_backup` 可能是很久以前的一次备份；IndexedDB/离线缓存被清空后，刷新只能从过期的备份恢复，**最近一段对话可能丢失**。
- **建议**：在 `clearCacheAndReload` 里、执行 `localStorage.clear()` 之前，先调用一次 `emergencySaveWithBeacon()`（或等价逻辑），把当前内存中的对话写入 `_emergency_backup`，再清空并刷新。这样清缓存后恢复的是“当前页”的最新状态。
- **实现**：已在 `clearCacheAndReload()` 确认后、清除前调用 `emergencySaveWithBeacon()`。

---

### 2. localStorage 写满时的紧急备份缩小【✅ 已缓解】

- **位置**：`js/conversations.js` — `emergencySaveWithBeacon()`。
- **逻辑**：先尝试写完整备份 `fullBackupData`；若 `localStorage.setItem` 抛错，再尝试只写当前角色 `minimalBackup`。
- **结果**：写满时只保留**当前角色**的对话；其他角色的未同步对话在关页/杀进程后会**无法从紧急备份恢复**。
- **建议**：
  - 在降级到 minimal 时用 `console.warn` 明确提示“仅保存当前角色，其他角色未写入”。
  - 可选：按角色逐个写更小的块（例如按 charId 分 key），在 quota 紧张时尽量多保留几个角色（需评估 key 数量和大小）。
- **实现**：已增加 `console.warn` 与 `showToast` 提示“存储空间不足，仅保存了当前角色对话”/“本地存储已满，无法保存对话备份”。

---

### 3. 多标签页共享同一紧急备份（恢复后被“消费”）【✅ 已修复】

- **位置**：`js/conversations.js` — `tryRecoverConversationsFromBackup` / `tryRecoverGalgameFromBackup`。
- **逻辑**：从备份恢复某角色后，会从备份对象中 `delete backup.conversations[charId]`（或 galgame），再 `writeEmergencyBackupToAllSources(backup)`，相当于该角色从备份中“被消费”。
- **场景**：标签页 A 先加载角色 1，从备份恢复并写回“已去掉角色 1”的备份；标签页 B 再加载角色 1 时，从磁盘读到的备份里已无该角色，**B 无法再从紧急备份恢复**，可能看到空对话。
- **建议**：
  - 恢复后写回“已消费”备份时，可考虑用 `BroadcastChannel` 通知其他标签页“某角色已从备份恢复”，其他页可更新本地对备份的认知或提示用户。
  - 或者：多标签下不从备份中删除该角色，只在本页标记“已恢复”，这样其他页仍可从备份恢复（可能重复恢复，需在合并时去重或按 timestamp 合并）。
- **实现**：恢复后不再从备份中删除该角色、不写回“已消费”备份，其他标签页仍可从同一份备份恢复；本页恢复后通过 BroadcastChannel 发送 `emergency_recovery_applied`，其他标签页若正在查看该角色会从备份刷新。

---

### 4. 恢复后写回备份时部分成功

- **位置**：`js/conversations.js` — `writeEmergencyBackupToAllSources`；`tryRecoverConversationsFromBackup` / `tryRecoverGalgameFromBackup`。
- **逻辑**：恢复时先 `delete backup.xxx[charId]`，再写 localStorage / Android / IndexedDB。若 localStorage 成功、其余失败，不会抛错（内部 catch），磁盘上已是“缩小后”的备份。
- **结果**：若之后某次“全部源”的读取只来自 localStorage，则只能拿到缩小后的备份；其他角色在该备份中已不可见。通常还会从 Android/IndexedDB 读，`loadEmergencyBackupFromAllSources` 取最新 timestamp，所以只有当地址空间里 localStorage 的备份更新而其他源未更新时才会出现不一致。
- **建议**：保持当前“取最新”逻辑；若观测到多源不一致，可考虑“合并多源”而不是仅选最新一份，以减少单源失败导致整份备份变小的风险。

---

### 5. 登出时主动清空（符合预期）

- **位置**：`js/auth.js` — `resetAppState()`。
- **逻辑**：`window.conversations = {}`、清 DOM、`clearEmergencyBackup()`。
- **结论**：这是预期行为，避免跨用户泄露；不视为“意外丢失”，无需改逻辑。

---

### 6. 后端“只读模式”与空内容

- **位置**：`js/conversations.js` — `saveConversationsToBackend`。
- **逻辑**：`save_intent === 'auto_sync'` 且没有任何对话/ galgame 要保存时，不发送保存请求，改为调用 `loadConversationsFromBackend()` 从数据库拉一次。
- **结论**：避免用“空”自动覆盖后端；若数据库有内容会拉回并刷新。不会导致后端被清空。

---

### 7. 离线 / 懒加载时对 `window.conversations` 的赋值

- **位置**：`js/characters.js` — 从 API 或 IndexedDB 加载后对 `window.conversations` 的赋值。
- **逻辑**：按角色合并（只设置 `data.messages` 里出现的 charId），不先整体清空再赋值；未知格式时保留现有数据。
- **结论**：不会因一次加载就清空其他角色的对话；暂无发现误清空路径。

---

### 8. Android 杀进程后 localStorage 被清空

- **位置**：`js/auth.js` 注释；`js/conversations.js` — 紧急备份写 Android + localStorage。
- **现状**：紧急备份已双写；`loadEmergencyBackupFromAllSources` 会从 Android 与 localStorage 取最新。若杀进程后 localStorage 被清空，仍可从 Android 恢复备份。
- **结论**：设计上已考虑该场景；需确保 Android 端 `saveToDisk`/`loadFromDisk` 在进程被杀前被调用（例如在 `onPause`/`onStop` 时由原生侧写入）。

## 四、建议优先实现的修改（✅ 已完成）

1. **✅ 清缓存前先紧急备份**  
   在 `clearCacheAndReload()` 中，在清除任何存储之前调用 `emergencySaveWithBeacon()`（若存在），保证“清空并刷新”后能从最新状态恢复。  
   **实现**：`js/utils/system-utils.js` 已在确认后、清空前执行 `window.emergencySaveWithBeacon()`。

2. **✅ localStorage 写满时的提示**  
   在 `emergencySaveWithBeacon()` 中，当降级为 `minimalBackup` 时打 `console.warn`，并在条件允许时用 `showToast` 提示用户“存储空间不足，仅保存了当前角色对话”。  
   **实现**：`js/conversations.js` 中降级为 minimal 或完全写入失败时均调用 `showToast` 提示。

3. **✅ 多标签页恢复策略**  
   - 恢复后**不再从备份中删除该角色、不写回“已消费”备份**，其他标签页仍可从同一份备份恢复（`tryRecoverConversationsFromBackup` / `tryRecoverGalgameFromBackup` 不再 `delete` + `writeEmergencyBackupToAllSources`）。  
   - 本页从紧急备份恢复后，通过 **BroadcastChannel** 发送 `emergency_recovery_applied`；其他标签页若正在查看该角色且模式一致，会再次调用 `loadConversationDetail` 从备份刷新，避免空对话。

完成以上三点后，在各种情况和边缘场景下，对话记录被意外清空或丢失的概率会明显降低；其余逻辑（后端防误删、前端合并、登出清空）已较为稳妥。

## 五、补充审查：更多边缘情况（2025 年复查）

以下为对「各种情况和边缘下是否仍有丢失/清空可能」的补充审查结论。

### 9. 关页/切后台时防抖未执行即卸载

- **位置**：`js/conversations.js` — `handlePageUnload` / `handleVisibilityChange`；`saveConversationsToBackend` 的防抖逻辑。
- **逻辑**：`handlePageUnload` 会先 `clearTimeout(window._saveDebounceTimer)` 并置空，再调用 `saveConversationsToBackend({ immediate: true, emergency: true })` 和 `emergencySaveWithBeacon()`。
- **结论**：关页或切后台时不会因防抖未到点而跳过保存；紧急保存与本地备份都会执行，**不会因防抖导致丢失**。

### 10. 保存进行中又触发紧急保存（锁竞争）

- **位置**：`js/conversations.js` — `saveConversationsToBackend` 内 `window._isSavingData` 与 `_pendingEmergencySave`。
- **逻辑**：若 `_isSavingData` 为 true 且本次为 emergency，会设置 `_pendingEmergencySave = true`；在 `finally` 里当前保存完成后会再执行一次紧急保存。
- **结论**：紧急保存在锁内被排队重试，**不会因“正在保存”而丢一次保存**。

### 11. 紧急备份 24 小时后被清除

- **位置**：`js/core/init.js` — 紧急恢复逻辑中 `backupAge > 24 * 60 * 60 * 1000` 时 `localStorage.removeItem('_emergency_backup')`。
- **结论**：属**预期行为**，避免用超过 24 小时的旧备份覆盖当前状态；不视为意外丢失。

### 12. 清空缓存时 IndexedDB 被整体删除

- **位置**：`js/utils/system-utils.js` — `clearCacheAndReload` 中 `offlineCache.clearAllCache()` 与 `indexedDB.deleteDatabase('RolePlayOfflineCache')`。
- **逻辑**：清空前已执行 `emergencySaveWithBeacon()`；`CLEAR_CACHE_PRESERVE_KEYS` / `ALWAYS_PRESERVE_KEYS` 会保留 `_emergency_backup` 在 localStorage，清空后恢复仅依赖 localStorage 的备份。
- **结论**：设计如此，**清缓存后仍可从 localStorage 紧急备份恢复**；若希望也从 IndexedDB 恢复，需在清空时同样保留 IndexedDB 中的紧急备份（当前未保留，属已知取舍）。

### 13. load_characters / loadConversationsFromBackend 全量覆盖同一角色

- **位置**：`js/conversations.js` — `loadConversationsFromBackend` 按 `data.messages` 的 charId 遍历并执行 `window.conversations[charId] = list`；`js/characters.js` 中从 API 加载后同样按角色赋值。
- **逻辑**：只对**出现在响应中的角色**赋值，不先清空整个 `window.conversations`，因此不会误清“未在本次响应中的角色”。但对**同一角色**会用本次响应的 list 直接覆盖。
- **当前后端**：`/api/load_characters` 在 lazy 与非 lazy 下均返回 `messages: {}`，对话实际由 `/api/conversation/detail` 按需加载，因此当前不会发生“全量接口返回更少对话导致覆盖变少”的情况。
- **理论风险**：若日后在 `load_characters` 中返回全量/部分对话，且某次返回的某角色对话数少于本地已有，则会直接覆盖为该较少列表，**存在该角色对话变少的可能**。建议：后端若扩展全量加载，应保证全量一致性；前端可考虑在“同一角色对话数变少”且非 user_edit 时做一次合并或确认（需与多端删除同步权衡）。

### 14. 删除对话后多标签页同步备份

- **位置**：`js/conversations.js` — `initCrossTabDeleteSync` 中通过 BroadcastChannel 收到删除后，从 `loadEmergencyBackupFromAllSources()` 取备份，filter 掉已删对话，再 `writeEmergencyBackupToAllSources(backup)`。
- **逻辑**：删除会在所有持有备份的源上更新为“已去掉该对话”的备份，避免其他标签页恢复时再出现已删对话。
- **边缘**：若 `writeEmergencyBackupToAllSources` 仅部分成功（例如 localStorage 成功、Android/IndexedDB 失败），多源取最新时可能某源仍含已删对话，恢复时可能短暂再现。与第 4 点一致，**理论低概率**，可接受或后续做多源合并。

### 15. 离线路径下 window.conversations 被整块替换

- **位置**：`js/characters.js` — 离线时从 IndexedDB（及紧急备份合并）得到 `convsToUse`，执行 `window.conversations = convsToUse`。
- **逻辑**：整块替换仅发生在**离线首次加载**，数据来源为 IndexedDB + 紧急备份合并，不依赖当前内存中的 conversations，因此不会误删已加载的其他角色。
- **结论**：**不会因离线替换导致意外丢失**；替换的是“离线态下的完整快照”。

### 16. clearAllCache 会清掉 META 中的紧急备份

- **位置**：`js/core/offline-cache.js` — `clearAllCache()` 会清空所有 store（含 META），IndexedDB 中的 `_emergency_backup` 会丢失；`system-utils.js` 随后还会 `deleteDatabase('RolePlayOfflineCache')`。
- **结论**：与第 12 点一致：清缓存后紧急恢复仅依赖 **localStorage** 中保留的 `_emergency_backup`，设计如此。

### 17. 登录后空缓存先展示 + 网络中断导致“所有对话显示为空”【✅ 已修复】

- **位置**：`js/conversations.js` — `shouldUseOfflineCacheForOverwrite`；`loadConversationDetail` 中“先应用缓存再 Revalidate 网络”。
- **场景**：登录后懒加载只拉角色列表；用户点进某角色时，本地缓存（Android/IndexedDB）里该角色是**空对话**；逻辑原先会“立即应用缓存”再发网络请求。若此时请求被中断（如切后台、ERR_CONNECTION_ABORTED），则界面已显示空且网络未返回，用户会以为“对话全丢了”。
- **结论**：**已修复**。在 `shouldUseOfflineCacheForOverwrite` 中增加：**在线且缓存为空时，不应用空缓存**，直接等待网络；网络成功则用服务器数据，失败再按原有离线逻辑处理，避免“空缓存先展示 + 请求中断”导致一直显示空。

## 六、补充小结表

| 场景 | 是否可能丢失/清空 | 严重程度 | 说明 |
|------|-------------------|----------|------|
| 关页时防抖未执行 | 否 | - | 关页会取消防抖并立即执行紧急保存 + 紧急备份 |
| 保存锁与紧急保存竞争 | 否 | - | 紧急保存会排队在 finally 中重试 |
| 紧急备份 24h 后清除 | 否（预期） | - | 故意不恢复过旧备份 |
| 清缓存后 IndexedDB 无备份 | 否 | - | 已保留 localStorage 紧急备份 |
| load_characters 返回更少对话覆盖 | 理论可能 | 低 | 当前接口不返回对话；若日后扩展需保证全量一致或前端合并策略 |
| 删除对话后多源备份部分写入 | 理论可能 | 低 | 与第 4 点一致 |
| 离线加载整块替换 conversations | 否 | - | 替换的是离线快照，不会误删已加载数据 |
| clearAllCache 清掉 IndexedDB 紧急备份 | 已知 | - | 清缓存后仅依赖 localStorage 备份 |
| 登录后空缓存先展示 + 网络中断 | 是（显示为空） | 中 | ✅ 已修复：在线且缓存为空时不应用空缓存，等待网络 |

**总体结论**：在现有实现下，文档第四、五、六节覆盖的场景中，**无明显新增的“意外丢失或清空”路径**；仅存在理论上的低概率边缘（如后端日后返回部分数据导致单角色覆盖变少、多源备份部分写入不一致），可在后续迭代中按需加强（如全量一致性保证或多源合并）。

## 七、服务端/流式边缘情况（2026-02 复查）

### 18. 流式模式下模型 API 异常时未持久化【✅ 已修复】

- **位置**：`backend/routes/chat.py` — 流式 producer 内 `httpx.ConnectError` / 通用 `Exception` 分支。
- **逻辑**：异常时向客户端发送友好错误提示后直接 `return`，未调用 `run_conversation_persistence`，本回合（用户消息 + 系统错误提示）只存在于前端内存。
- **结果**：若用户此后未触发同步（如关页、强杀）且未再发消息，该回合不会落库，存在丢失可能。
- **实现**：在 ConnectError / Exception 分支中，将 `full_content = friendly_msg` 后执行与正常流结束相同的持久化流程（`run_conversation_persistence` + save_status + [DONE]），再 return。异常时本回合也会写入数据库。

### 19. 客户端流式中途断开

- **位置**：同上 — producer 使用 `_put_sse` 且队列满时 `put_nowait` 丢弃，不阻塞。
- **结论**：producer 独立于消费端运行，会跑完并执行持久化；客户端断开不会导致本回合不保存。

### 20. 前端强杀 / 崩溃未触发 beforeunload

- **场景**：进程被系统或用户强杀（如任务管理器结束、浏览器崩溃），`beforeunload` / `pagehide` / `visibilitychange` 可能不触发。
- **结果**：自上次成功同步或紧急备份以来的**仅存于内存**的对话，无法写回后端或紧急备份，可能丢失。
- **缓解**：后端在每次流式结束（含异常）都会持久化该回合；前端在发消息、AI 回复、切后台等时机触发同步与紧急备份，可降低“最后几轮未同步”的窗口。无法在纯前端完全避免强杀导致的丢失。

### 21. 一角色全链路单一 id【✅ 已实施】

- **策略**：不再出现「同一角色多 id」（如 short id / originalId_timestamp / 前缀回退）。从大厅添加角色时分配**唯一 UUID** 作为该角色的 id，对话、Galgame、同步等全链路只使用此 id。
- **修改**：
  - **character_hall.py**：`add_character_from_hall` 使用 `new_char['id'] = str(uuid.uuid4())`；已存在判断改为按 `originalId === character_id`（不再按 id 前缀）。
  - **characters.py**：`get_conversation_detail` 仅按 `target_id` 精确加载，移除 Galgame/普通对话的前缀、回退加载；Galgame 保存仅用前端传入的 `char_id`，不再做 `load_galgame_data_resolved` 解析。
  - **galgame_dao**：`reset_galgame_data` 仅按 `char_id` 精确重置；`load_galgame_data_by_char_id_prefix` / `load_galgame_data_resolved` 保留于 DAO 层供兼容或脚本使用，主 API 不再调用。
  - **utils.py**：`load_galgame_state_async` 仅调用 `load_galgame_data`，不再前缀回退。
  - **conversations_dao**：`get_conversation_count` 仅按 `character_id = ?` 精确统计。
- **结果**：新添加的角色在全链路只有一个 id，避免因多 id 导致的误覆盖、对话消失等问题。

### 22. 游戏模式（Galgame）整段对话消失、显示开始界面【✅ 已由 §21 根除】

- **原因**：此前同一角色在 DB 中可能有多条记录（短 id / 完整 UUID 等），加载时取到空记录会导致 `messages: []`、前端显示开始界面。
- **现状**：实施「一角色全链路单一 id」（§21）后，从大厅添加角色即分配唯一 UUID，对话/Galgame 仅按该 id 读写，不再产生多 id、无前缀回退，从根源上避免整段对话消失。DAO 层仍保留 `load_galgame_data_by_char_id_prefix` 等函数供脚本或历史数据兼容，主 API 已不再调用。

## 八、再次检查（迁移后，用户与服务器边缘情况）

在完成「一角色一 id」、流式异常持久化、全量迁移后，对**仍可能丢失角色对话数据**的路径做复核。

### 已覆盖的防护（仍有效）

| 类别 | 防护 |
|------|------|
| 后端防误删 | `save_intent=auto_sync` 禁止用更少消息/对话覆盖；`user_edit` 或专用删除/重置才可减量。 |
| 后端加载 | 对话/Galgame 仅按精确 `character_id` 读写，无前缀/回退，不会取错行。 |
| 流式持久化 | 正常结束、ConnectError/Exception 均执行 `run_conversation_persistence`；客户端中途断开不阻塞 producer，会照常落库。 |
| 持久化前加载失败 | `run_conversation_persistence` 内若加载现有对话失败则**不保存**，避免用「仅本条」覆盖历史。 |
| 前端空不覆盖 | `save_intent=auto_sync` 且无内容时不发保存，改为 `loadConversationsFromBackend` 拉取。 |
| 前端合并 | 服务器为空时保留本地；本地更新时 SmartMerge；后端为空时尝试从紧急备份恢复（`tryRecoverConversationsFromBackup` / `tryRecoverGalgameFromBackup`）。 |
| 关页/切后台 | 取消防抖 + 立即 `saveConversationsToBackend({ emergency: true })` + `emergencySaveWithBeacon()`。 |
| 保存中再紧急保存 | `_pendingEmergencySave` 在 `finally` 中重试，不丢一次。 |
| 清缓存前 | `clearCacheAndReload` 先执行 `emergencySaveWithBeacon()`，再清空。 |
| 多标签备份 | 恢复后不消费备份，BroadcastChannel 通知；localStorage 写满有提示。 |
| 在线空缓存 | 在线且缓存为空时不应用空缓存，等待网络，避免「空缓存 + 请求中断」显示为空。 |

### 仍可能丢失或需接受的边缘情况

| 场景 | 是否可能丢失 | 严重程度 | 说明 |
|------|----------------|----------|------|
| **前端强杀/崩溃未触发 beforeunload** | 是 | 中 | 自上次同步或紧急备份以来**仅存于内存**的对话无法写回。后端每回合会落库，可缩小窗口；无法在纯前端完全避免。 |
| **localStorage 写满** | 是（非当前角色） | 中 | 紧急备份降级为仅当前角色，其他角色未写入备份；已有 console + showToast。 |
| **多源紧急备份部分写入失败** | 理论可能 | 低 | 多源取最新，单源失败时可能读到较旧一份；可接受或后续做多源合并。 |
| **迁移后未刷新且备份 key 为旧 id** | 是（一次性） | 低 | 紧急备份用 `charId` 作 key；迁移后角色为新 UUID，备份里若仍是旧 id，恢复时 `backup.conversations[new_id]` 为空。建议用户迁移后**刷新或重新登录**一次。 |
| **服务器 COMMIT 前崩溃** | 否 | - | SQLite 事务回滚，下次前端重试同步即可。 |
| **DB 写入返回失败** | 否（有重试） | - | 前端 `_lastSaveFailed` + visibility/online 时重试；紧急备份仍会写。 |

### 再次检查小结

- **服务端**：一角色一 id、精确读写、流式（含异常）落库、加载失败不覆盖，已无明显「误删/误覆盖」路径。
- **用户端**：强杀/崩溃导致未执行 beforeunload 时，仅存于内存的增量可能丢失；localStorage 写满时非当前角色无法进入紧急备份。其余场景有关页/切后台紧急保存、空不覆盖、从备份恢复等防护。
- **迁移后**：建议用户刷新或重新登录一次，使前端角色 id 与库一致，避免旧 id 的备份无法匹配新 id。
