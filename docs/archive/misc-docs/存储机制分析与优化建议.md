# 存储机制分析与优化建议

## 📊 当前存储架构概览

### 1. 对话记录存储

#### 前端存储
- **内存存储**：`window.conversations` 对象
  ```javascript
  window.conversations = {
    "charId": [
      {
        id: "conv_timestamp",
        title: "对话标题",
        timestamp: 1234567890,
        version: 1,
        messages: [...]
      }
    ]
  }
  ```

- **本地缓存**：
  - **IndexedDB**：通过 `offline-cache.js` 管理，支持大容量离线存储
    - 数据库名：`RolePlayOfflineCache`
    - 存储结构：`conversations` store（按 `username_charId` 为 key）
  - **Android 原生存储**：优先使用（容量大，异步，不阻塞）
  - **LocalStorage**：已弃用（空间限制导致性能问题）

#### 后端存储
- **文件系统**：按用户/角色/对话分文件存储
  ```
  user_data/
    {username}/
      conversations/
        {charId}/
          {convId}.json  # 每个对话一个文件
  ```
- **旧格式兼容**：
  - `conversations/{charId}.json`（单文件多对话）
  - `conversations.json`（大文件，所有角色）

#### 同步机制
- **实时同步**：WebSocket（`sync.js`）
- **批量同步**：`/api/save_characters` 和 `/api/load_characters`
- **离线缓存**：IndexedDB 后台同步（`offline-cache.js`）

---

### 2. 用户设置存储

#### 前端存储
- **LocalStorage**：`chatSettings` key
  ```javascript
  localStorage.setItem('chatSettings', JSON.stringify(settings));
  ```

#### 后端存储
- **文件系统**：`user_data/{username}/settings.json`

#### 同步机制
- **API 同步**：`/api/user/settings`（GET/POST）
- **异步同步**：前端保存时自动触发云端同步

---

### 3. 角色信息存储

#### 前端存储
- **内存存储**：`window.characters` 数组
- **本地缓存**：
  - **IndexedDB**：`characters` store（按 username 为 key）
  - **Android 原生存储**：优先使用

#### 后端存储
- **文件系统**：`user_data/{username}/characters.json`
- **默认角色**：`character_data/characters.json`

#### 同步机制
- **批量同步**：通过 `/api/save_characters` 和 `/api/load_characters`
- **实时同步**：WebSocket 广播变更事件

---

## 🔍 当前架构的优缺点分析

### ✅ 优点

1. **简单直接**：文件系统存储，无需数据库配置
2. **易于备份**：直接复制 `user_data` 目录即可
3. **离线支持**：IndexedDB 提供完整的离线缓存能力
4. **多端同步**：WebSocket 实现实时多设备同步
5. **性能优化**：按对话分文件，避免大文件加载
6. **图片优化**：使用占位符减少传输大小

### ⚠️ 缺点

1. **查询性能**：文件系统查询需要遍历目录，无法快速索引
2. **并发控制**：文件锁机制（`galgame_locker`）可能成为瓶颈
3. **数据一致性**：多文件操作可能出现不一致
4. **扩展性**：文件数量增长后，文件系统性能下降
5. **搜索功能**：难以实现全文搜索、时间范围查询等
6. **数据统计**：需要遍历所有文件才能统计
7. **备份恢复**：需要手动处理，无法增量备份

---

## 🚀 优化建议

### 方案一：引入 SQLite 数据库（推荐）

#### 优势
- ✅ **零配置**：SQLite 是文件数据库，无需独立服务
- ✅ **高性能**：索引查询比文件遍历快得多
- ✅ **ACID 事务**：保证数据一致性
- ✅ **SQL 查询**：支持复杂查询和统计
- ✅ **向后兼容**：可以保留文件系统作为备份

#### 实施步骤

1. **数据库设计**
   ```sql
   -- 用户表
   CREATE TABLE users (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       username TEXT UNIQUE NOT NULL,
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   );

   -- 角色表
   CREATE TABLE characters (
       id TEXT PRIMARY KEY,
       user_id INTEGER NOT NULL,
       name TEXT NOT NULL,
       avatar TEXT,
       prompt TEXT,
       bio TEXT,
       data TEXT,  -- JSON 格式的完整角色数据
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

   -- 对话表
   CREATE TABLE conversations (
       id TEXT PRIMARY KEY,
       character_id TEXT NOT NULL,
       user_id INTEGER NOT NULL,
       title TEXT NOT NULL,
       timestamp INTEGER NOT NULL,
       version INTEGER DEFAULT 1,
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (character_id) REFERENCES characters(id),
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

   -- 消息表
   CREATE TABLE messages (
       id TEXT PRIMARY KEY,
       conversation_id TEXT NOT NULL,
       role TEXT NOT NULL,
       content TEXT NOT NULL,
       image_url TEXT,
       timestamp INTEGER NOT NULL,
       message_id TEXT UNIQUE,  -- 消息唯一ID
       sequence_number INTEGER,
       previous_message_id TEXT,
       suggestions TEXT,  -- JSON 数组
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (conversation_id) REFERENCES conversations(id)
   );

   -- 用户设置表
   CREATE TABLE user_settings (
       user_id INTEGER PRIMARY KEY,
       settings TEXT NOT NULL,  -- JSON 格式
       updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

   -- Galgame 数据表
   CREATE TABLE galgame_data (
       character_id TEXT PRIMARY KEY,
       user_id INTEGER NOT NULL,
       score INTEGER DEFAULT 40,
       status TEXT DEFAULT 'playing',
       updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (character_id) REFERENCES characters(id),
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

   -- Galgame 消息表
   CREATE TABLE galgame_messages (
       id TEXT PRIMARY KEY,
       character_id TEXT NOT NULL,
       user_id INTEGER NOT NULL,
       role TEXT NOT NULL,
       content TEXT NOT NULL,
       image_url TEXT,
       timestamp INTEGER NOT NULL,
       message_id TEXT UNIQUE,
       sequence_number INTEGER,
       previous_message_id TEXT,
       is_hidden INTEGER DEFAULT 0,
       created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
       FOREIGN KEY (character_id) REFERENCES characters(id),
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

   -- 索引
   CREATE INDEX idx_conversations_character ON conversations(character_id);
   CREATE INDEX idx_conversations_user ON conversations(user_id);
   CREATE INDEX idx_conversations_timestamp ON conversations(timestamp);
   CREATE INDEX idx_messages_conversation ON messages(conversation_id);
   CREATE INDEX idx_messages_timestamp ON messages(timestamp);
   CREATE INDEX idx_galgame_messages_character ON galgame_messages(character_id);
   CREATE INDEX idx_galgame_messages_timestamp ON galgame_messages(timestamp);
   ```

2. **迁移策略**
   - 保留现有文件系统代码
   - 新增数据库访问层（DAO）
   - 逐步迁移：新数据写入数据库，旧数据按需迁移
   - 双写模式：同时写入数据库和文件（过渡期）

3. **代码示例**
   ```python
   # backend/db/database.py
   import sqlite3
   import aiosqlite
   import json
   from typing import Optional, List, Dict
   
   class Database:
       def __init__(self, db_path: str = "ponychat.db"):
           self.db_path = db_path
       
       async def init(self):
           async with aiosqlite.connect(self.db_path) as db:
               # 创建表结构
               await db.executescript(SCHEMA_SQL)
               await db.commit()
       
       async def save_conversation(self, username: str, char_id: str, conversation: dict):
           async with aiosqlite.connect(self.db_path) as db:
               # 获取用户ID
               user_id = await self._get_user_id(db, username)
               
               # 保存对话
               await db.execute(
                   "INSERT OR REPLACE INTO conversations (id, character_id, user_id, title, timestamp, version) VALUES (?, ?, ?, ?, ?, ?)",
                   (conversation['id'], char_id, user_id, conversation['title'], conversation['timestamp'], conversation.get('version', 1))
               )
               
               # 保存消息
               for msg in conversation.get('messages', []):
                   await db.execute(
                       "INSERT OR REPLACE INTO messages (id, conversation_id, role, content, image_url, timestamp, message_id, sequence_number, previous_message_id, suggestions) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)",
                       (msg.get('id'), conversation['id'], msg['role'], msg['content'], msg.get('image_url'), msg['timestamp'], msg.get('message_id'), msg.get('sequence_number'), msg.get('previous_message_id'), json.dumps(msg.get('suggestions', [])))
                   )
               
               await db.commit()
       
       async def load_conversations(self, username: str, char_id: str) -> List[dict]:
           async with aiosqlite.connect(self.db_path) as db:
               user_id = await self._get_user_id(db, username)
               
               async with db.execute(
                   "SELECT id, title, timestamp, version FROM conversations WHERE user_id = ? AND character_id = ? ORDER BY timestamp DESC",
                   (user_id, char_id)
               ) as cursor:
                   conversations = []
                   async for row in cursor:
                       conv_id, title, timestamp, version = row
                       
                       # 加载消息
                       async with db.execute(
                           "SELECT role, content, image_url, timestamp, message_id, sequence_number, previous_message_id, suggestions FROM messages WHERE conversation_id = ? ORDER BY sequence_number",
                           (conv_id,)
                       ) as msg_cursor:
                           messages = []
                           async for msg_row in msg_cursor:
                               messages.append({
                                   'role': msg_row[0],
                                   'content': msg_row[1],
                                   'image_url': msg_row[2],
                                   'timestamp': msg_row[3],
                                   'message_id': msg_row[4],
                                   'sequence_number': msg_row[5],
                                   'previous_message_id': msg_row[6],
                                   'suggestions': json.loads(msg_row[7]) if msg_row[7] else []
                               })
                       
                       conversations.append({
                           'id': conv_id,
                           'title': title,
                           'timestamp': timestamp,
                           'version': version,
                           'messages': messages
                       })
                   
                   return conversations
   ```

### 方案二：优化现有文件系统架构

如果暂时不想引入数据库，可以优化现有架构：

#### 1. 引入消息队列
- 使用 Redis 或内存队列缓冲写入
- 批量写入文件，减少文件锁竞争

#### 2. 改进索引机制
- 维护元数据索引文件（`user_data/{username}/.index.json`）
- 记录对话ID、时间戳、角色ID等快速查询信息

#### 3. 实现增量备份
- 使用 Git 或 rsync 实现增量备份
- 定期压缩旧对话文件

#### 4. 优化查询性能
- 缓存常用查询结果
- 使用内存映射文件（mmap）加速读取

---

### 方案三：混合架构（最佳实践）

结合文件系统和数据库的优势：

1. **数据库存储**：
   - 对话元数据（ID、标题、时间戳）
   - 消息索引和元数据
   - 用户设置
   - 角色信息

2. **文件系统存储**：
   - 大文件（图片、附件）
   - 完整对话JSON（作为备份）
   - 历史归档数据

3. **优势**：
   - 快速查询（数据库）
   - 大文件管理（文件系统）
   - 数据安全（双重备份）

1. **短期**：优化文件系统查询性能（索引文件）

建议优先实施 **SQLite 数据库方案**，因为：
- 零配置，易于部署
- 性能提升明显
- 支持复杂查询
- 向后兼容现有架构
