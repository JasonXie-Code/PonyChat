# 小游戏 - 中国象棋设计

> 文档状态：2026-08-09 已复核。本文作为设计或测试规范继续保留；条目是否已实现以 `docs/PROJECT_STATUS.md` 和代码为准。

## 目标

中国象棋小游戏不是一个单纯的棋盘工具，而是普通对话关系的延伸。用户进入对局后，角色仍然应该保持原本的语气、关系、记忆和互动习惯，同时具备清晰的下棋风格、棋力表现和对局反馈。

当前阶段先设计中国象棋的对战体验、准备步骤、开局等待方式、角色语音开关、用户消息入口，以及后续执行步骤的 JSON 协议。真正的棋力策略和服务端持久化可以后续分阶段实现。

## 核心体验

用户在普通聊天输入栏中点击“中国象棋”后，直接进入对局页。对局页不应该让用户停在明显的 loading 页面，而是用“摆棋动画”自然覆盖准备步骤的等待时间。

进入后界面结构为：

1. 顶部栏：沿用普通对话模式顶部栏的系统栏处理方式，正常显示时间、电量、信号等系统信息。
2. 角色区域：显示角色头像、名字、执棋方、当前状态、角色气泡，以及可选的语音回复开关。
3. 棋盘区域：显示中国象棋棋盘，支持红黑视角翻转。
4. 底部栏：更多按钮、消息按钮、用户名字和头像。
5. 输入栏：点击消息按钮后，在底部栏下方展开普通对话样式的输入栏，但隐藏普通聊天里的图片、相机、表情、快捷回复、更多工具按钮。

键盘升起时，棋盘和角色区域不应移动。键盘只影响底部输入栏。中国象棋 Activity 应使用 `SOFT_INPUT_ADJUST_NOTHING`，底部栏自行处理 IME inset。

## 对局入口流程

点击“中国象棋”后：

1. 客户端立即进入中国象棋界面。
2. 棋盘先显示为空棋盘。
3. 前台播放 5.5-6 秒摆棋动画。
4. 后台并行运行“准备步骤”，生成本局使用的短角色卡。
5. 摆棋完成后等待准备步骤给出本局角色卡。
6. 首次可见角色发言由执行步骤生成：角色执红方时开场白与第一步棋同轮输出，角色执黑方时输出纯开场白后等待用户先走。
7. 如果准备步骤失败或超时，静默降级到默认角色卡，不打断用户。

准备步骤不生成可见开场白；所有会展示给用户、可能提到具体走法的开场内容都必须在执行步骤中产生。

## 摆棋动画

摆棋动画用于同时提供仪式感和遮罩准备步骤等待时间。

建议总耗时控制在 5.5-6 秒。棋子一个一个出现，使用轻微的透明度和缩放动画：

```text
alpha: 0 -> 1
scale: 1.18 -> 1.0
单枚间隔: 80-140ms
```

推荐落子顺序：

1. 双方九宫核心：将/帅、士/仕、象/相。
2. 车、马、炮。
3. 兵、卒。
4. 用户所执方最后几枚略慢，强化“这是你的棋”的感觉。

摆棋期间：

1. 用户不能走棋。
2. 底部栏可以显示，但消息和更多操作可以先弱化或禁用。
3. 角色气泡可以显示：“我先把棋摆好，顺便想想今天该怎么和你下这一局。”

摆棋结束后：

1. 允许用户走棋。
2. 如果准备步骤已完成，更新角色气泡。
3. 如果准备步骤未完成，使用默认气泡，例如：“我走好了，轮到你。”

## 准备步骤

准备步骤是在进入中国象棋时立即后台运行的一次普通对话大模型调用。它生成一份本局使用的配置型角色卡，用于给后续对局回复频率、语气强度、候选走法偏好和棋风决策提供上下文。它不是完整角色 prompt，也不是执行步骤本体。

准备步骤不再输出大段自然语言资料卡。模型可以参考约 400 字规模的上下文，但最终 JSON 应以级别参数、枚举、概率和少量短句为主。这样日志更像配置文件，执行步骤也更容易稳定消费。

准备步骤的输入材料：

1. 角色基础设定：名字、简介、prompt、头像、语音配置。
2. 最近对话：最近 20-50 条，重点提取称呼、语气、关系状态。
3. 长期记忆：用户偏好、角色对用户的印象、固定互动习惯。
4. 小游戏历史：井字棋、中国象棋或其他小游戏中的胜负、让棋、悔棋、调侃方式。
5. 当前局设置：用户执红/黑、是否开启角色语音回复。

准备步骤配置应重点回答：

1. 角色对用户的关系和称呼。
2. 角色在对局中的说话频率、能量、玩笑程度和回复长度。
3. 角色的下棋风格、风险偏好、攻防倾向。
4. 角色棋力档位、计算深度和角色化失误倾向。
5. 角色赢、输、将军、失误、被悔棋时的反应枚举。
6. 可以延续的历史互动梗，但只能作为短 hook。

准备步骤直接复用普通对话模式使用的大模型与模型配置，但使用小游戏专用 system/user prompt 和 JSON 输出约束。请求、原始模型响应、解析结果、耗时和错误都需要写入 `.chatlogs`，日志模式建议使用 `chinese_chess`，阶段名建议使用 `XIANGQI_PREPARE_REQUEST`、`XIANGQI_PREPARE_RESPONSE`、`XIANGQI_PREPARE_PARSED`。

准备步骤和执行步骤都必须关闭思考。请求日志中应能看到 `enable_thinking=false` 或等价的 `thinking.type=disabled`。

内部建议直接使用结构化 JSON 存储，不再压缩成中文长卡片。

准备步骤 prompt 不应给模型一整段可复制的示例 JSON，尤其不能给低 `speech.frequency` 或高 `silent_move_rate` 的示例值。更安全的写法是列字段约束和数值解释，让模型自己根据角色资料填值。

字段约束：

1. `schema_version`：固定为 `2`。
2. `relationship`：包含 `familiarity`、`warmth`、`teasing`、`address_mode`、`raw_username_policy`。
3. `speech`：包含 `frequency`、`verbosity`、`energy`、`playfulness`、`comforting`、`max_reply_chars`。
4. `chess_style`：包含棋力、计算深度、风险偏好、攻防倾向、失误倾向。
5. `reaction`：包含将军、被将军、赢、输、失误、悔棋时的反应枚举。
6. `execution_policy`：包含沉默走棋概率、普通走棋说话概率、吃子/将军说话概率、候选偏好排序。
7. `memory_hooks`：短 hook 数组，没有合适记忆时为空。

`speech.frequency` 的含义：

```text
0 几乎不说
1 很少说
2 偶尔说
3 正常说
4 话多
5 非常话多
```

`execution_policy` 必须和 `speech.frequency` 一致。活泼、话多、外向、派对型角色通常 `frequency` 为 4-5，`silent_move_rate` 应较低，普通走棋多数应该说话；冷静、寡言、严肃角色才适合更高的沉默走棋概率。

## 准备步骤缓存

同一用户和同一角色可以缓存准备步骤资料卡，避免每次进入都重新生成。

建议缓存 key：

```text
user_id + character_id + minigame_type + card_version
```

触发重新生成的情况：

1. 最近对话有明显更新。
2. 长期记忆有更新。
3. 用户和角色完成了一局小游戏。
4. 角色基础设定或语音设定发生变化。
5. 准备步骤资料卡版本升级。

缓存可以先用本地或服务端简单存储，后续再加入摘要 hash 判断。

## 对局界面

### 顶部栏

顶部栏应和普通对话模式一致：

1. 正常承接系统状态栏背景。
2. 显示时间、电量、信号等系统状态。
3. 状态栏图标明暗跟随顶部栏背景。
4. 标题为“中国象棋”。
5. 左侧返回。
6. 不在顶部暴露重置按钮，避免操作分散。

### 角色区域

角色区域显示：

1. 角色头像。
2. 角色名字。
3. 角色执棋方，例如“执黑方”。
4. 当前局状态，例如“红方行棋”“黑方思考中”“红方胜”。
5. 角色气泡。
6. 语音回复按钮。

语音按钮规则：

1. 只有角色支持语音时显示。
2. 支持语音的判断可以先使用：`voiceEnabled == true || voiceId 不为空`。
3. 按钮位于角色气泡右侧区域。
4. 点击后高亮，表示本局角色语音回复开启。
5. 再次点击关闭。
6. 这个开关是当前对局会话内状态，不需要立即改写角色全局设定。

### 棋盘区域

棋盘需要支持：

1. 红方视角。
2. 黑方视角。
3. 点击棋子显示可走目标。
4. AI 思考中禁止用户操作。
5. 摆棋动画期间禁止用户操作。

用户执黑时，棋盘下方应是黑子，上方是红子。棋盘坐标显示可以翻转，但内部逻辑坐标必须保持固定，避免模型和棋规引擎混乱。

### 底部栏

底部栏排布：

```text
更多按钮    消息按钮                       用户名字 + 用户头像
```

底部系统导航栏颜色应与底部栏背景保持一致。

更多菜单包含：

1. 重置棋盘。
2. 调转方向。
3. 悔棋。
4. 当前执棋项，例如“我执红方”或“我执黑方”。

“我执红方/我执黑方”不应显示为两个菜单项。菜单只显示当前状态，点击后切换为另一方；下次打开菜单时显示新的状态。

菜单项不显示图标，保持轻量。

### 消息输入

点击消息按钮后，在底部栏下方展开输入栏。输入栏复用普通对话模式的输入框和发送按钮视觉：

1. 胶囊输入框。
2. 圆形发送按钮。
3. 不显示图片、相机、表情、快捷回复、更多工具按钮。
4. 键盘升起时，角色区域和棋盘不移动。
5. 发送后可收起输入栏，也可根据体验保留，当前建议发送后收起。

## 用户发消息让角色操作棋子

用户可以在对局中给角色发消息，例如：

```text
你可以让一下我吗？
你下一步准备怎么走？
别太认真嘛。
我想悔一步。
```

当前阶段可以先做本地占位回复。后续接入模型后，用户消息应进入执行步骤，模型返回结构化 JSON，决定是否只聊天、是否走棋、是否更新下一步计划。

注意：用户消息不应绕过棋规。即使模型说要走某一步，也必须由棋规引擎校验。

## 执行步骤 JSON 协议

执行步骤是每次角色需要回应、思考或行棋时运行的普通对话大模型调用。它同样复用普通对话模式使用的大模型与模型配置，但使用小游戏专用 prompt、当前棋局、准备步骤配置和候选走法列表作为输入。执行步骤输出 JSON，核心原则是把“角色怎么说”和“棋局怎么动”分开。

执行步骤的请求、原始模型响应、解析结果、非法走法原因、修正结果和 fallback 信息都需要写入 `.chatlogs`。日志模式建议使用 `chinese_chess`，阶段名建议使用 `XIANGQI_EXECUTE_REQUEST`、`XIANGQI_EXECUTE_RESPONSE`、`XIANGQI_EXECUTE_PARSED`、`XIANGQI_EXECUTE_RETRY`。

### 候选走法选择器

大模型不直接生成象棋走法。下棋系统先根据当前棋盘计算合法走法，并从中挑出最多 5 个不同倾向的候选，再交给模型选择。

候选建议包含：

1. `best`：搜索评估下的最佳走法。
2. `good`：稳定但不一定最强的好选择。
3. `risky`：有进攻、吃子或将军倾向，但风险更高。
4. `blunder`：合法但较差的“看错棋/角色化失误”候选。
5. `random`：随机合法候选，用于增加变化。

模型的任务是根据准备步骤配置、用户消息、角色性格和局面，从候选中选择 `selected_move_id`，并决定是否说话。即使模型返回了坐标，客户端也应优先以候选 id 对应的走法为准。

推荐 schema：

```json
{
  "schema_version": 2,
  "action": "move",
  "selected_move_id": "c1",
  "character_reply": {
    "text": "我先用炮压一下中路，看看你怎么应。",
    "tts_text": "我先用炮压一下中路，看看你怎么应。",
    "emotion": "confident_playful",
    "style_tags": ["主动", "轻松", "带一点得意"]
  },
  "move": {
    "from": {"x": 1, "y": 2},
    "to": {"x": 4, "y": 2},
    "piece": "炮",
    "notation": "炮二平五",
    "intent": "控制中路",
    "confidence": 0.78
  },
  "next_plan": {
    "summary": "如果你不处理，我会继续压中路。",
    "candidate_move": {
      "from": {"x": 0, "y": 0},
      "to": {"x": 0, "y": 1},
      "notation": "车一进一"
    },
    "targets": ["中路", "用户左翼马"]
  },
  "ui": {
    "highlight_cells": [
      {"x": 1, "y": 2},
      {"x": 4, "y": 2}
    ],
    "show_thinking": false
  },
  "safety": {
    "confidence": 0.74,
    "needs_legal_retry": false
  },
  "private": {
    "brief_reason": "该走法发展子力，同时对中路形成压力。",
    "risk_level": "medium"
  }
}
```

### action

`action` 表示这次模型回复的类型：

```text
move              说话并走棋
move_silent       只走棋，不说话
chat_only         只聊天，不走棋
ask_clarification 请求用户澄清
offer_draw        提和
resign            认输
```

### character_reply

`character_reply.text` 是第一人称气泡内容，直接展示给用户。它应该短、自然、有角色味，不要变成长篇棋理分析。

`tts_text` 用于语音回复。角色语音开关关闭时可以忽略；开启时交给语音系统。

### move

`move` 是当前准备执行的走法。它必须使用固定逻辑坐标，不受棋盘翻转影响。当前实现中，`move` 只是模型回显或补充说明，真正执行应以 `selected_move_id` 对应的候选为准。

建议内部坐标：

```text
x: 0..8
y: 0..9
红方初始在 y=9
黑方初始在 y=0
```

模型返回的 `selected_move_id` 和 `move` 都只能作为候选选择结果。客户端或服务端棋规引擎必须检查：

1. from 上是否有棋子。
2. 棋子是否属于当前行棋方。
3. to 是否在棋盘内。
4. 是否符合棋子走法。
5. 是否导致己方被将军。
6. 是否与当前局面一致。
7. `selected_move_id` 是否来自本次 `move_candidates`。

如果非法，进入重试或 fallback 流程。

### next_plan

`next_plan` 是角色下一步倾向，不等于必然走法。因为用户下一步可能改变局势，所以 `next_plan.candidate_move` 只能作为心理预告或风格参考。

角色可以用 `next_plan.summary` 在气泡中透露一点计划，但不应总是暴露完整意图，否则对局会失去博弈感。

### private

`private` 可存储简短理由、风险、模型自评等，不展示给用户。不要把完整 chain-of-thought 放入这里，只保留可调试的简短说明。

## 非法走法处理

模型返回非法 `selected_move_id`、未选择候选，或候选校验失败时，不应直接展示给用户。

推荐流程：

1. 棋规引擎校验失败。
2. 优先从本次候选列表中选择 fallback，例如 `best`。
3. 如需更精细，可以将当前局面、非法原因和原 JSON 发给模型做一次轻量修正，只要求重选 `selected_move_id`。
4. 如果重试仍失败，使用本地 AI 或棋规搜索 fallback 生成合法走法。
5. 角色气泡可以沿用原 `character_reply.text`，也可以替换成通用语句：“嗯，我换个更稳的走法。”

最大重试次数建议为 1-2 次，避免用户等待过久。

## 棋力与难度

用户界面不暴露难度调整。棋力由后台策略、准备步骤资料卡和系统设定共同决定。

准备步骤资料卡可以描述棋风和智力，但不要让用户看到类似“难度 8”“失误率 18%”的内部参数。

可以在后端配置：

1. 基础棋力。
2. 角色化失误概率。
3. 计算深度。
4. 是否偏好进攻、防守、交换、诱导。
5. 是否允许让棋。

## 状态与数据

一个中国象棋对局建议包含：

```json
{
  "game_id": "uuid",
  "user_id": "user",
  "character_id": "character",
  "player_side": "red",
  "character_side": "black",
  "board": "current board state",
  "turn": "red",
  "move_history": [],
  "character_card": {},
  "completed_game_records": [],
  "game_memory": {},
  "voice_reply_enabled": false,
  "created_at": 0,
  "updated_at": 0
}
```

早期可以只保存在客户端内存里。后续如果需要恢复对局、统计小游戏经历、生成更好的准备步骤资料卡，应保存到服务端。

小游戏历史可以摘要为：

```json
{
  "game_type": "xiangqi",
  "result": "user_win",
  "player_side": "black",
  "notable_events": ["用户悔棋一次", "角色主动让出中兵", "用户喜欢问角色下一步计划"],
  "relationship_delta": "轻松愉快"
}
```

这些历史摘要会成为下一次准备步骤资料卡的输入。

当前对局页内还应维护一份跨局象棋记忆，传给准备步骤和执行步骤：

1. `latest_game.summary`：一句自然语言摘要，用来快速回答“上一局怎么样”并影响下一局的情绪、调侃和不服气程度。
2. `latest_game.capture_stats`：结构化吃子账本，按 `user_captured_character` 和 `character_captured_user` 分开统计，`by_kind.soldier` 用于回答“上一局我吃了你几个兵/卒/小兵”这类精确问题。
3. `latest_game.moves` / `key_moments`：保留最近若干步和关键吃子、将军、角色走法，用来回答“上一局我怎么赢的”“你那步为什么悔棋”等具体追问。
4. `latest_game.dialogue`：保留局内关键对话，让角色能延续赌气、玩笑、劝悔棋、投降等互动语气。

跨局记忆只能描述过去对局，不能当成本局棋盘事实。模型回答“上一局/上盘/刚才那局”时应查 `game_memory.latest_game`，不要从当前棋盘倒推。

## 分阶段实现建议

### 第一阶段：界面与本地体验

1. 完成中国象棋 UI。
2. 用户可选择红黑方。
3. 底部栏、消息输入、更多菜单、语音按钮完成。
4. 棋盘方向正确。
5. 摆棋动画完成。
6. 准备步骤先使用本地 mock 或后台占位。

### 第二阶段：准备步骤生成

1. 点击中国象棋后后台运行准备步骤。
2. 生成输入包括角色基础设定、最近对话、记忆、小游戏历史。
3. 支持缓存。
4. 准备步骤资料卡只影响后续执行步骤的语气、棋风和候选偏好，不生成角色第一句气泡。

### 第三阶段：执行步骤 JSON 回复

1. 接入执行步骤返回 JSON。
2. 客户端或服务端校验走法。
3. 非法走法重试或 fallback。
4. 角色气泡、走棋动画、语音回复由 JSON 驱动。

### 第四阶段：长期小游戏记忆

1. 对局结束生成小游戏历史摘要。
2. 摘要进入角色和用户记忆。
3. 下一次准备步骤资料卡引用这些经历。
4. 角色逐渐形成稳定的对局风格和共同回忆。

## 关键原则

1. 对局体验优先，不让用户等纯 loading。
2. 棋规必须由确定性引擎校验，不能完全信任模型。
3. 准备步骤负责角色味道，不负责全部棋力。
4. 执行步骤 JSON 负责结构化控制，不直接等于最终执行结果。
5. 用户界面不暴露后台难度参数。
6. 键盘、输入栏、系统栏处理方式要和普通对话模式保持一致。
7. 语音回复是对局内开关，只有角色支持语音时显示。
