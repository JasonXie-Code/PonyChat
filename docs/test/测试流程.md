# PonyChat 测试流程

使用 $ponychat-test-workflow 继续

本文档用于规范 PonyChat 的前端、后端、网页和角色回复测试。目标是让每次修复都有明确的定位、隔离验证、真实环境验收和清理记录。

## 1. 核心原则

1. **内容修复优先修材料**
   - 不加代码级别的兜底替换、正则改写或输出清洗。
   - 角色回复内容问题优先通过提示词、字段结构、材料传递和事实边界修复。
   - Step 3 只作为“看材料写回复”的执行层，不应该依赖 Step 3 修正上游错误材料。

2. **后端真实验收必须在 Server-USA**
   - 修改后端代码、提示词、字段结构、API、任务或数据库读写后，先做本地静态验证，再部署到 Server-USA。
   - 必须看到 health 的 `deploy_token` 与本次部署一致，确认新进程加载了新代码。
   - 服务器测试命令使用 `/opt/ponychat/.venv/bin/python`。
   - 不用本机服务或本地大模型调用作为后端角色回复的最终验收。

3. **后端测试必须隔离真实数据**
   - 每轮测试使用全新的随机测试用户。
   - 测试用户会员等级设为 `developer`。
   - 不直接请求 System 用户下的角色 ID。
   - 必须先把 System 用户下的目标角色临时克隆到随机测试用户下面，再请求临时克隆角色。
   - 测试完成后必须清理随机测试用户、临时克隆角色、测试对话、消息、普通对话记忆、角色记忆、情绪状态、图片上下文、关系状态、主动任务、用量记录、会员记录等测试数据。

4. **App 修改必须安装到本机模拟器验收**
   - 修改 Android App 后，必须构建 APK，安装到本机模拟器，并在模拟器里验证真实页面、状态恢复和交互结果。
   - 只看代码、Compose 预览或静态截图不算完成。

5. **网页修改必须部署到真实承载环境验收**
   - 修改网页外观、网页功能、WebView 资源或服务器承载的前端资源后，本地预览只能作为设计确认。
   - 最终必须部署到对应服务器或实际承载环境，并打开真实 URL 验证资源已更新、行为已生效。

6. **所有测试必须留原文和证据**
   - 不能只写“通过/失败”。
   - 测试输出必须保留原始输入、原始输出、check 结果、failures 列表、截图/录屏/API 响应或数据库检查结果。

## 2. 测试类型入口

开始处理问题前，先判断测试类型，并选择对应流程。

| 类型 | 典型问题 | 必须验收方式 |
| --- | --- | --- |
| Android App 纯 UI | 样式、布局、滚动、加载态、空态、导出图片、主题色 | 构建 APK，安装到本机模拟器验证 |
| Android App 状态/持久化 | 冷启动、重进 App、切换页面、图片/语音/草稿/任务状态恢复 | 模拟器冷启动、热启动、杀 App 重进验证 |
| 网页/WebView 资源 | 网页外观、网页功能、服务器承载的前端资源 | 本地预览后部署到真实承载环境验证 |
| 后端字段/API | 结构化字段、关系页、记忆、任务、用量、会员、图片上下文 | 本地静态验证后部署 Server-USA，用隔离测试数据验证 |
| 后端角色回复 | 回复跑偏、上下文串台、状态不稳定、场景/记忆/关系材料错误 | Server-USA 上随机 developer 用户 + 克隆 System 角色矩阵验证 |
| 混合端到端 | App 操作触发后端，再由 App 展示结果 | 后端 Server-USA 验证 + App 模拟器验证 |

## 4. Android App 测试流程

### 4.1 适用范围

- 原生 Android 页面、Compose UI、WebView 容器、聊天页、关系页、快捷消息面板、表情包面板、设置页。
- 加载态、空态、滚动、底栏同步、面板切换、图片/语音/导出渲染。
- 本地缓存、冷启动、杀 App 重进、页面返回、旧数据兼容。

### 4.2 本地静态验证

```powershell
cd P:\PonyChat\Android-App
.\gradlew.bat :app:compileDebugKotlin
.\gradlew.bat :app:assembleDebug
```

- 涉及单元测试或已有 instrumentation 测试时，补跑对应测试。
- 只是预览网页或 HTML 参考稿时，也要截图确认浅色和深色都符合预期。

### 4.3 安装到本机模拟器

```powershell
adb devices
adb install -r -d P:\PonyChat\Android-App\app\build\outputs\apk\debug\app-debug.apk
adb shell am force-stop top.ponychat.webview
adb shell monkey -p top.ponychat.webview 1
```

验收要求：

- 必须确认 `adb install` 返回 `Success`。
- 冷启动问题必须先 `force-stop`，再从 launcher 或 `monkey` 进入。
- 如果问题涉及重进 App，必须杀 App 后再次进入验证。

### 4.4 App 矩阵建议

| 维度 | 场景 |
| --- | --- |
| 主题 | 浅色、深色 |
| 数据状态 | 加载中、空数据、正常数据、错误态、旧缓存数据 |
| 进入方式 | 冷启动、热启动、从列表进入、从详情返回、杀 App 后重进 |
| 消息表现 | 普通消息、主动消息、单条、多条瞬发、多条延迟、图片消息、语音消息 |
| 页面表现 | 聊天页、关系页、快捷消息面板、表情包面板、导出图片、设置页 |
| 屏幕条件 | 默认模拟器尺寸、窄屏、长文本、大图片、长语音识别文本 |

### 4.5 App 验收重点

- 加载完成前显示加载态，不闪空态。
- 空提示只在加载完成且确实无数据时出现。
- 文本不溢出、不重叠、不被底栏遮挡。
- 浅色和深色模式下文字、图标、边框、背景对比度足够。
- 切换面板、返回页面、冷启动后状态一致。
- 图片、语音、导出内容在重进 App 后仍能显示。
- 自动滚动只在用户位于底部时触发；多条瞬发只做一次滚动。
- 如果页面资源由服务器提供，必须部署到服务器后验证真实页面；本地预览只能确认方向。

### 4.6 App 留证模板

```text
  - name:
    passed:
    evidence:
```

## 5. 网页/WebView 资源测试流程

### 5.1 适用范围

- 独立网页、WebView 页面、服务器承载的 HTML/CSS/JS/图片资源。
- 外观调整、交互调整、资源缓存、线上页面展示。

### 5.2 本地预览

- 本地 HTML 或 localhost 只能用于设计方向确认。
- 需要检查浅色、深色、移动端宽度、长文本、空数据、加载态和错误态。
- 视觉稿或参考网页可以保留在 `var` 目录，但不能作为最终上线验收。

### 5.3 部署验收

- 修改被服务器承载的网页或 WebView 资源后，必须部署到对应服务器或实际承载环境。
- 部署后打开真实 URL 验证资源版本、样式和交互已经生效。
- 如果 App 内 WebView 会加载该资源，还需要在模拟器 App 内打开对应页面验证。

### 5.4 通过标准

- 本地预览通过。
- 真实 URL 资源已更新。
- App WebView 入口展示一致。
- 缓存不会导致旧资源继续显示。

## 6. 后端字段/API 测试流程

### 6.1 适用范围

- 字段定义、字段传递、结构化输出、schema、DAO、API 返回、数据库落库。
- 关系页、记忆、任务、用量、会员、图片上下文、主动任务状态。

### 6.2 先定位问题

- 判断问题来自字段定义、字段传递、数据库状态、接口返回、提示词材料还是模型执行层。
- 如果 `.chatlogs` 可用，先读取相关轮次的 Step 1、Step 2、Step 3 请求和响应。
- 当前日志目录：`P:\PonyChat\var\ChatMonitor\.chatlogs`。
- 如果是结构化字段问题，先看字段进入模型前是否已经错误，再看模型输出是否违反约束。

### 6.3 本地静态验证

```powershell
python -m py_compile Backend\path\to\changed_file.py
python -m pytest Backend\tests\test_xxx.py
```

- 字段裁剪、schema、归一化、DAO、API 返回优先用单元测试覆盖。
- 本地测试只确认代码、提示材料、字段结构正确。
- 不用本地模型调用当最终验收。

### 6.4 部署到 Server-USA

```powershell
python Backend\deploy\deploy_backend_server_usa.py
```

必须确认：

- health 返回的 `deploy_token` 与本次部署一致。
- 后端服务已重启并进入 active 状态。
- 新代码已经被服务器进程加载。

### 6.5 隔离测试数据

- 每轮测试创建全新的随机测试用户。
- 会员等级设为 `developer`。
- 用户资料按测试需要设置，比如人类、小马、无特殊资料等。
- 测试结束必须清理，并检查：
  - `left_user = 0`
  - `left_chars = 0`
  - `left_conversations = 0`
  - `left_messages = 0`
  - `left_normal_chat_memory = 0`
  - `left_character_memories = 0`

### 6.6 字段/API 矩阵建议

| 维度 | 场景 |
| --- | --- |
| 输入值 | 正常值、空值、缺字段、旧字段、超长值、重复值、边界值 |
| 用户状态 | 新用户、老用户、无历史对话、有历史对话 |
| 上下文状态 | 有图片上下文、有主动任务、有关系状态、有记忆 |
| 接口行为 | 写入接口、读取接口、重算接口、缓存命中、缓存失效 |
| 一致性 | 数据库落库值、API 返回值、App 展示值三者一致 |

### 6.7 字段/API 留证模板

```text

请求：
响应：
数据库检查：

  - name:
    expected:

    passed:
```

### 6.8 字段/API 通过标准

- 字段约束类：边界值和旧数据兼容必须通过。
- 数据落库类：写入、读取、重进程后读取必须一致。
- 展示供给类：API 返回必须能直接被 App 使用，不要求 App 再做语义修正。

## 7. 后端角色回复测试流程

### 7.1 适用范围

- 角色回复跑偏。
- 引用过期上下文。
- 把用户行为归因给角色。
- 场景串台。
- 身体状态、醉酒、体力、关系、记忆或图片上下文没有正确重置。
- Step 1/2 材料错误或 Step 3 在正确材料下执行不稳定。

### 7.2 先定位错误来源

从 `.chatlogs` 找到出错轮次，把 Step 1、Step 2、Step 3 请求和响应都看一遍。

判断规则：

- Step 1/2 已经给错材料：修提示词、字段、材料传递。
- Step 3 自己幻觉：修 Step 3 输出字段或执行提示。
- 记忆/场景错误：修记忆摘要、场景锚点、事实边界。

不要直接按最终回复打补丁，先找错误材料从哪一步进入。

### 7.3 本地静态验证

```powershell
python -m py_compile Backend\path\to\changed_file.py
python -m pytest Backend\tests\test_xxx.py
```

- 本地只确认代码、提示材料和字段结构正确。
- 不用本地大模型调用当验收结果。

### 7.4 部署后真实验证

每次真实验证前都先部署：

```powershell
python Backend\deploy\deploy_backend_server_usa.py
```

部署要求：

- 必须看到 health 的 `deploy_token` 一致。
- 测试命令使用服务器环境：`/opt/ponychat/.venv/bin/python`。
- 不用本机服务验证后端角色回复。

### 7.5 克隆 System 角色

- 不直接请求 System 用户下的角色 ID。
- 先把 System 角色临时克隆到随机测试用户下面。
- 测试请求只使用临时克隆角色。

默认 smoke 角色：

- 紫悦
- 碧琪
- 柔柔

高风险或上线前回归角色：

- 紫悦
- 碧琪
- 珍奇
- 苹果嘉儿
- 云宝
- 柔柔

### 7.6 场景矩阵

角色之间可以并发执行，单个角色内部按场景顺序执行，便于定位失败。

默认每个问题设计 3 类场景：

| 场景 | 目的 |
| --- | --- |
| direct_fact | 直接询问核心事实，确认角色使用正确材料 |
| correction_challenge | 用户给一个错误说法，确认角色不会顺着错材料走 |
| natural_scene | 放进普通对话或剧情里，确认模型稳定应用约束 |

复杂问题可以扩展到 5 个场景，但先用 3 角色控制成本。

需要避免只测试用户遇到的原始句子，应该加入相似但不相同的安全内容测试。

### 7.7 推荐测试设计格式

```text
问题：
修复点：
期望不变量：
禁止项：
测试角色：
测试场景：
1. direct_fact:
   user:
   expected:
   forbidden:
2. correction_challenge:
   user:
   expected:
   forbidden:
3. natural_scene:
   user:
   expected:
   forbidden:
通过标准：
清理检查：
```

### 7.8 输出必须保存原文

每个测试输出必须包含：

- 测试用户。
- 克隆角色 ID。
- 原始用户问题。
- 原始角色回复。
- 每条 check 的结果。
- failures 列表。
- cleanup 结果。

推荐输出格式：

```text
SUMMARY:
ROLE_RESULTS:
  role:
  cloned_character_id:
  scenarios:
    key:
    raw_user_message:
    raw_role_reply:
    checks:
    failures:
FAILURES:
CLEANUP:
  left_user:
  left_chars:
  left_conversations:
  left_messages:
  left_normal_chat_memory:
  left_character_memories:
```

### 7.9 验收标准

- 单点修复：3 角色 × 3 场景全过，或者真实问题复现上下文必过。
- 模糊判断类问题：90% 以上通过即可。
- 高风险流程改动：先 3 角色 smoke，通过后再 6 角色矩阵。
- 如果失败是模型偶发但材料正确，记录原文，先观察。
- 如果失败来自 Step 1/2 错材料，继续修流程。

## 8. 可复用矩阵组件

新增后端角色回复矩阵时，优先复用：

- `Backend/scripts/matrix_test_common.py`

新脚本只需要保留三类内容：

- `SCENARIO_KEYS`：场景 key 列表。
- `build_scenario(char, key)`：构造 `ScenarioInput`，写清原始用户问题和上下文消息。
- `validate_step(key, result, scenario, char)`：返回 `passed/checks/failures/raw_role_reply`。

公共组件统一处理：

- 创建随机 developer 测试用户。
- 克隆 System 角色到测试用户。
- 角色并发、角色内场景顺序执行。
- 标准化输出 `SUMMARY / ROLE_RESULTS / FAILURES / CLEANUP`。
- 清理用户、克隆角色、对话、消息、记忆、情绪/场景/图片状态、关系状态、主动任务、用量和会员记录，并在 cleanup 非 0 时失败。

推荐样板：

- `Backend/scripts/test_choice_attribution_matrix.py`

## 9. 端到端问题处理顺序

遇到 App + 后端混合问题时，按以下顺序处理：

1. 确认问题是否能由 App 本地状态复现。
2. 如果能本地复现，先修 App，并安装到模拟器验证。
3. 如果涉及后端字段或角色回复，先看 `.chatlogs`，确认错误材料来自哪一步。
4. 后端改完后，先本地静态验证，再部署 Server-USA。
5. 使用随机 developer 用户和临时克隆角色做服务器测试。
6. 如果 App 展示也受影响，再安装最新 APK 到模拟器做端到端验证。
7. 清理所有测试数据，并记录 cleanup 结果。

## 10. 清理标准

后端测试结束必须清理以下数据：

- 随机测试用户。
- 临时克隆角色。
- 测试对话。
- 测试消息。
- 普通对话记忆。
- 角色记忆。
- 情绪状态。
- 场景状态。
- 图片上下文。
- 关系状态。
- 主动任务。
- 用量记录。
- 会员记录。

最低通过条件：

```text
left_user = 0
left_chars = 0
left_conversations = 0
left_messages = 0
left_normal_chat_memory = 0
left_character_memories = 0
```

如果 cleanup 结果非 0，测试不能视为完成。
